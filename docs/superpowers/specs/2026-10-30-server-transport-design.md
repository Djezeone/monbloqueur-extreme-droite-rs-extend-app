# B CONNECT — transport Mastodon côté serveur

30 octobre2026, Europe/Paris. Base PR#4 au42a70ca, deux CI vertes et socle durable conservé. Ce lot ajoute une frontière réseau réellement exécutable en Node24 et testée en HTTPS local. Aucun serveur n'est provisionné/déployé, aucune route publique ni intégration PWA activée, aucune requête vers un compte social réel, aucun coût supplémentaire.

## Décision et alternatives
Choix de l'agent dans le mandat d'autonomie : Node natif `https.request` et session en fermeture mémoire serveur. Aucun secret dans le frontend. Le `fetch` générique/SDK susceptible de répéter un POST ne convient pas au contrat sans rejeu ; installer un backend géré sans coût/accès établis n'est pas autorisé. Ni login OAuth, ni PKCE/DPoP maison, ni révocation fournisseur ne sont construits ici. Le jeton doit être fourni par un futur composant OAuth serveur qualifié : les métadonnées/type locaux ne prouvent pas son obtention officielle.

## Interfaces et limites fixes
- `server/connectors/network-policy.js` exporte normalizeOrigin(value), isPublicAddress(address), selectPublicAddress(results), normalizeMastodonRequest(input,origin). Erreurs ConnectorError `server-*`, sans entrée brute.
- Origine HTTPS/DNS canonique,443 seulement, sans identifiants/chemin/query/hash/IP littérale/nom local. Liste d'origines administrateur requise,32maximum ; aucune découverte utilisateur implicite.
- IPv4 : exclure tous les blocs spéciaux IANA et224/4multicast. IPv6 : autoriser2000::/3 sauf2001::/23,2001:db8::/32,2002::/16,2620:4f:8000::/48,3fff::/20. Politique conservatrice : certains spéciaux mondialement accessibles sont refusés. Liste DNS1..16objets `{address,family}` ; tous doivent être publics/cohérents, pas seulement l'adresse choisie.
- Entrée transport exacte : url,method,redirect:'error',credentials:'omit', signal facultatif et body facultatif. Aucun en-tête/options arbitraires. URL absolue canonique et origine liée. Quatre routes Mastodon4.3+ seulement : GET verify_credentials sans query/body ; GET relationships avec exactement id[]=ID et with_suspended=true, sans body ; POST accounts/ID/block ou unblock, sans query, body objet vide. ID décimal strict existant.
- Résultat de normalizeMastodonRequest : `{url,method,path,targetId,action}` ; targetId/action null sur identité, targetId sur relation, action block/unblock sur POST.
- `server/connectors/mastodon-transport.js` exporte createMastodonTransport({origin,allowedOrigins,accountId,accessToken,scopes,ttlMs=900000,timeoutMs=10000,maxBodyBytes=65536,now=Date.now,lookup=dns.promises.lookup,request=https.request}). Dépendances réseau/horloge injectées de confiance ; aucune option test/bypass TLS en production.
- Scopes exactement profile/read:follows/write:blocks ; identifiant décimal, token Bearer syntaxique1..4096caractères capturé uniquement dans fermeture serveur. TTL local1..3600000ms, aucun auto-refresh ; n'est pas la durée du token Mastodon. Timeout total1..30000ms DNS→corps ; corps128..1048576octets ; en-têtes16KiB.
- Handle gelé : `{session,transport,status,disconnect}`. session métadonnées figées compatibles avec l'adaptateur existant, sans token ; status rend état/localExpiresAt/active uniquement. Aucun sérialiseur/export/reprise de secrets. Disconnect invalide les handles, interrompt les requêtes et retire la référence au token ; aucune promesse d'effacement physique mémoire ni révocation fournisseur. État terminal sans réactivation implicite.

## Envoi et réponses
Une seule requête active par handle ; aucun appel au chargement. Résoudre DNS une fois avec all:true/verbatim:true, valider tout le jeu puis épingler une adresse via lookup privé. Conserver hostname/Host/SNI d'origine et rejectUnauthorized:true, aucun checkServerIdentity permissif ; family explicite/autoSelectFamily:false, agent:false. Construire **un ClientRequest et un end** par transport : aucun fallback DNS, redirection, retry, refresh. Ce n'est pas une garantie de livraison exactement une fois chez le fournisseur.

Vérifier arrêt/TTL/signal après DNS et juste avant dispatch. Annulation/timeout avant dispatch : aucun socket ; après dispatch : effet POST incertain. Abort détruit request/response ; timeout total, pas simplement l'événement socket.401/403 arrêtent le handle dès les en-têtes et avant toute lecture de corps, sans divulguer le corps. Retour non200 minimal `{}` et seuls Retry-After/X-RateLimit-Reset bornés ; aucune Location/cookie/message fournisseur. Une redirection421/503 n'est jamais suivie/répétée. Identité différente : arrêt.

Pour200 : JSON UTF-8 strict, type application/json et encodage absent/identity, taille bornée y compris chunked/troncation. Projeter uniquement les champs utilisés par l'adaptateur : identité `{id}` liée au compte ; relation `[{id,blocking}]` liée à la cible ; POST `{id,blocking}` lié à l'action. Réponse invalide après POST = incertain, jamais succès. Les confirmations restent une lecture fraîche de relation, pas une réponse POST ou un état de timeline.

## Validation et frontières non qualifiées
Tests unitaires de politique, tests de cycle/session et vrai serveur TLS loopback avec certificat éphémère. Un driver **de test** réoriente la connexion vers localhost après avoir vérifié le choix public/TLS : le module de production ne contient aucun bypass local. DNS/transport simulés pour fautes, aucune sortie sociale. Assembler adaptateur/exécuteur durable avec backend de journal de test ; aucune équivalence avec journal serveur durable déployé revendiquée.

Restent bloquants : OAuth serveur officiel et stockage de session durable, authentification/CSRF des futures routes, journal serveur qualifié, révocation, export/effacement/rétention, version d'instance réelle, comptes test autorisés et egress/cloud/proxy. Bluesky reste derrière son SDK officiel/DPoP/PAR et frontière sans retry non qualifiés. PWA locale/SW/dépendances inchangés, main/admin, preview/coût, physique/WCAG et RGPD toujours ouverts.
