# Cohérence locale V3.2

Cette évolution répond à un échec constaté pendant la recette WebKit : après deux ajouts concurrents, les deux formulaires étaient vidés alors qu'un troisième onglet ne retrouvait qu'un ajout. La trace instrumentée suivante a passé ; elle ne prouve donc pas la cause interne du moteur. Le test de faute déterministe injecte des lectures de stockage périmées et retarde les événements : l'ancien contrôle accepte un écrasement ; le nouveau doit refuser le second écrivain et préserver son brouillon.

## Protocole
Les listes et flux ont toujours **un seul snapshot** `fil-clair-v1` dans localStorage. Une base IndexedDB séparée `fil-clair-integrity-v1`, store `state`, clé `snapshot`, conserve seulement `{version:1,digest}` : l'empreinte SHA256 de la présence et du texte exact du snapshot attendu. Aucun nom de source, compte, historique, secret ou copie des données n'y est stocké. Cette empreinte locale n'est ni une signature, ni une sauvegarde, ni une preuve fournisseur. Ne pas la publier.

Dans le Web Lock exclusif existant : lecture/comparaison de la source ; contrôle des10Mo ; calcul des empreintes précédente/suivante ; transaction IndexedDB readwrite demandant la durabilité stricte ; comparaison de l'empreinte courante et réservation de la suivante **avant** l'unique écriture synchrone du snapshot. La transaction réussie doit être accusée avant cette écriture. Une ancienne lecture ne suffit plus à accepter une seconde sauvegarde. Une opération sans différence textuelle n'écrit rien.

Si `setItem` échoue atomiquement, la transaction remet l'empreinte précédente uniquement si la suivante est encore courante. L'échec d'ouverture, une entrée invalide, une incohérence, une panne de transaction ou un délai de5secondes refuse l'écriture ; aucun repli mémoire silencieux, réinitialisation ou réancrage automatique. Une panne entre réservation et écriture peut donc laisser le mode persistant bloqué. Préserver les données est prioritaire ; un navigateur qui n'offre pas ces capacités garde lecture/export et l'espace temporaire consenti.

L'erreur de stockage est interceptée dans le callback du Web Lock ; la recette Firefox vérifie l'absence de remontée globale d'une erreur de quota. L'export JSON demeure compatible V3 et n'inclut pas l'empreinte ; une restauration volontaire normale emprunte le même protocole. Un effacement dans FIL CLAIR écrit l'état vide et son empreinte, sans garder l'ancienne empreinte. Effacer les données du site retire aussi cette base ; désinstaller l'app n'est pas une preuve d'effacement.

## Reprise et limites
Fermer les autres onglets puis recharger peut rétablir une vue courante après conflit. Si une interruption laisse une empreinte sans snapshot correspondant : exporter la vue accessible/la source brute, vérifier le fichier, fermer **tous** les onglets FIL CLAIR, choisir soi-même d'effacer les données du site dans le navigateur, rouvrir un seul onglet puis restaurer la sauvegarde. Aucun effacement n'est effectué par l'agent ou automatiquement. Sans sauvegarde, ne pas promettre de récupération ; l'espace temporaire reste exportable.

Ce protocole suppose que les écrivains coopèrent avec cette version. Les anciens scripts, DevTools, extensions ou autres écritures hors protocole ne sont pas rendus sûrs par une empreinte. Fermer les anciens onglets avant mise à jour/rollback. Il ne garantit pas la persistance matérielle lors d'une panne OS, une résistance à du JavaScript malveillant de même origine, la conservation en navigation privée/éviction, ou la synchronisation entre appareils. Les tests physiques Safari/Android restent ouverts.

Recette :6scénarios de concurrence par moteur, dont lecture périmée forcée et témoin refusé/corrompu/interrompu ; les résultats réellement terminés figurent dans le journal V3.2, sans être anticipés ici. Aucun journal durable d'opérations sociales n'est implémenté par cette évolution.

## Continuations de l'interface — correctif du30octobre
La génération privée de l'espace invalide les imports encore en lecture après un remplacement réussi ; elle ne change ni la clé ni le format du snapshot/témoin. Une annulation, un refus ou une mutation ordinaire conserve la génération. Une sauvegarde terminée ne vide pas un nouveau brouillon saisi pendant l'attente. Ce garde de l'interface ne change pas les limites des écrivains anciens, du crash réservation→écriture, de l'éviction ou des appareils physiques. Les données historiques orphelines restent importables, mais leur déclaration n'est pas activée au nouvel ajout d'un profil absent. Preuves : [cycle des données locales](evidence/2026-10-30-local-data-lifecycle.md).
